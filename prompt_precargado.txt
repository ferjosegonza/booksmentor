## 🔄 Flujo Lógico para saber el idioma de las enseñanzas

1. **El idioma original de un libro** se almacena en `Libros.Idioma_original_id`
2. **Todas las enseñanzas** de ese libro están en ese idioma original (`Enseñanzas.Texto_original`)
3. **Cuando un usuario pide una enseñanza en otro idioma**:
   - El sistema verifica si existe en `Traducciones` para esa `Enseñanza_id` e `Idioma_id`
   - Si existe → la reutiliza
   - Si no existe → la genera (1 sola vez) y la guarda
4. **En el historial de envíos** se registra en qué idioma se envió cada enseñanza a cada usuario

## ✅ ¿Por qué esta normalización es superior?

| Problema con el diseño anterior | Solución con esta estructura |
|--------------------------------|------------------------------|
| `Frecuencia` era texto libre | ✅ Ahora es FK a `Cat_Frecuencias` |
| `Plan` era texto libre | ✅ Ahora es FK a `Cat_Planes` |
| `Idiomas` repetidos en múltiples tablas | ✅ Un solo `Cat_Idiomas` referenciado |
| No se sabía en qué idioma estaba el texto original | ✅ `Libros.Idioma_original_id` lo define claramente |
| Tags en texto plano | ✅ Tabla `Cat_Tags` + relación N:N |
| Estados escritos a mano | ✅ Catálogos de estados |
| Dificultad para cambiar un nombre de opción | ✅ Se cambia en UN SOLO lugar |
| Dificultad para saber qué planes existen | ✅ Consulta simple a `Cat_Planes` |

---

## 🚀 Ventajas de esta arquitectura

1. **Mantenibilidad**: Cambias un valor UNA VEZ y se actualiza en todos lados
2. **Escalabilidad**: Agregar un nuevo idioma, plan o frecuencia es INSERT en catálogo
3. **Integridad**: La base de datos garantiza que solo existan valores válidos
4. **Consultas eficientes**: Las FK permiten JOINs rápidos y exactos
5. **Internacionalización**: Los catálogos pueden tener nombres en diferentes idiomas
6. **Claridad**: El idioma de cada texto es siempre explícito (original en libro, destino en traducción)

> - `Fecha_envío` (Fecha/Hora, auto) - Cuándo se envió
> - `Fecha_respuesta` (Fecha/Hora) - Cuándo se respondió (si se hizo)
> - `Respuesta_admin` (Texto largo) - Respuesta del administrador (opcional)

---

## 🔍 Índices recomendados

Para consultas eficientes en `Sugerencias_Usuarios`:

| Índice | Campos | Propósito |
|--------|--------|-----------|
| `idx_sugerencias_usuario` | `Usuario_id` | Buscar sugerencias de un usuario específico |
| `idx_sugerencias_estado` | `Leído`, `Atendido` | Filtrar sugerencias pendientes |
| `idx_sugerencias_tipo` | `Tipo_id` | Filtrar por tipo de sugerencia |
| `idx_sugerencias_fecha` | `Fecha_envío` | Ordenar por fecha |

## 🔄 Flujo de uso de Sugerencias

```
1. Usuario envía sugerencia
   → Se crea registro en Sugerencias_Usuarios
   → Leído = false, Atendido = false

2. Administrador revisa panel
   → Ve lista de sugerencias pendientes (Leído = false)
   → Lee el mensaje

3. Administrador marca como "Leído"
   → Leído = true

4. Administrador toma acción
   → Si es sugerencia de libro: lo agrega a la cola de procesamiento
   → Si es reporte de error: lo investiga
   → Si es mejora: la evalúa

5. Administrador responde (opcional)
   → Completa Respuesta_admin y Fecha_respuesta
   → Atendido = true
```
